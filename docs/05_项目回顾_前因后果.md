# 工作流管理项目回顾（前因后果 / 方案演进 / 最终落地）

> 目标读者：未来继续迭代的开发者、将应用交接给团队的维护者、以及“只关心能不能用/怎么用”的业务使用者。  
> 时间范围：从“Streamlit 版本尝试”到“PySide6 桌面版落地”的完整过程。  
> 本文只记录关键决策与可复用的结论，不追求逐字还原聊天内容。

---

## 1. 背景：为什么要做“工作流管理”

业务侧真实痛点是“重复性分析/刷新/导出”任务太多，且过程碎片化：
- Python 脚本：清洗、计算、落库、出图等
- Excel（PowerQuery）：源文件更新后，需要自动刷新查询并保存产物
- Power BI Desktop：需要定期/触发刷新 PBIX 后导出或发布

希望把这些操作“编排成一个工作流”，做到：
- 可重复执行、可追溯（日志/历史）
- 可视化编排（步骤列表 + 依赖关系）
- 防误操作（编辑与运行分离）
- 先满足个人使用，未来可升级到内网小团队

---

## 2. 早期尝试：Streamlit 版本为什么不理想

### 2.1 使用 Streamlit 的初衷
- 低成本快速成型：Python 生态直接用、改完即刷新
- 本地部署简单：对个人用户门槛低

### 2.2 遇到的关键问题（导致迁移）
1) **UI 表达受限**  
   - 复杂布局（左中右固定 + 中区滚动 + 控件对齐）不够灵活  
   - 控件密度、间距、对齐、状态展示难做成“高级感”
2) **交互模型受限**  
   - 需要更强的窗口级交互：分割、折叠、固定侧栏、复杂表格行内操作等
3) **未来扩展受限**（尤其面向小团队）  
   - 权限/审计、后台任务队列、并发控制、资源占用治理等，最终仍会走“更工程化”的形态

结论：Streamlit 适合 PoC/轻看板，但“工作流编排 + 复杂桌面交互”更适合 Web 全栈或桌面 GUI。

---

## 3. 关键决策：选择 PySide6 桌面版（V1）

在“功能优先”的前提下，选型落到：
- **Python + Qt（PySide6）**：桌面 UI 更自由，能更好承载“编排 + 表格 + DAG + 日志”的复杂界面。
- **SQLite**：本地持久化足够稳定；未来迁移到服务端数据库成本可控。

> 对应文档：`工作流管理/00_需求确认清单.md`

## 4. V1 需求冻结（我们最终确认的范围）

### 4.1 必做功能（V1）
1) 工作流管理：新建/复制/删除/重命名  
2) 步骤类型：
   - Python 脚本
   - Excel PowerQuery 刷新
   - Power BI Desktop 刷新
   - 子工作流（一个工作流步骤可以引用另一个工作流）
3) 编排能力：依赖、并行、前置步骤、上下移动、复制/删除  
4) 运行控制：
   - 全流程运行
   - 从指定步骤开始
   - 只运行指定步骤
   - 重试失败步骤
5) 监控与可追溯：实时日志、步骤日志打开、运行历史

### 4.2 非紧迫（延后）
- 产物管理（归档/版本/生命周期）
- 多人权限与审计（为内网小团队预留）

> 对应文档：`工作流管理/00_需求确认清单.md`、`工作流管理/03_实施排期与里程碑.md`

## 5. 界面方案演进（从“可用”到“更好用/更好看”）

### 5.1 最终确认的布局骨架（不改大布局）
1) 左侧：整体可折叠  
   - 上：工作流列表 + 新建/复制/删除  
   - 中：编辑开关（防误操作）  
   - 下：运行控制（四种模式）
2) 中区：可上下滚动（解决控件堆叠/重叠）  
   - 上：基础配置（可折叠）  
   - 中：DAG 可视化（默认展开、固定高度） + 步骤列表（核心编辑区）  
   - 下：步骤详情编辑器
3) 右侧：基本固定（可折叠）  
   - 实时日志  
   - 运行历史

> 对应文档：`工作流管理/01_功能与界面说明.md`、`工作流管理/04_详细界面说明.md`

### 5.2 具体争议点与最终结论
- **中区滚动**：为了解决“控件重叠/挤压”，中区采用滚动容器，左右栏保持固定。  
- **基础配置折叠交互**：从“勾选框折叠”调整为“独立折叠按钮”，更直观、减少误触。  
- **步骤列表**：保留“原版信息密度与字段”，并把“上下移动”集成到行内操作，避免额外按钮区占空间。  
- **编辑开关**：必须回归。默认关闭编辑，开启后才允许增删改（避免误操作）。  
- **依赖/并行的含义**：
  - 依赖：用于表达“必须先完成哪些步骤才允许执行当前步骤”（DAG 也基于此绘制连线）。  
  - 并行：用于表达“在全局并行开启时，哪些步骤允许同时执行”；前置步骤不允许并行（确保关键门槛先过）。

## 6. 架构落地：模块拆分与职责边界

整体遵循“UI 不直接干活、编排层管流程、执行器做落地动作、数据层负责持久化”的分层原则：

1) UI 层（PySide6）：界面、输入校验、交互编排、状态展示  
2) 编排层（Workflow Engine）：依赖/并行/前置规则、四种运行模式、失败策略  
3) 执行器层（Executors）：Python / Excel PowerQuery / Power BI / 子工作流  
4) 数据层（SQLite）：工作流/步骤/运行记录/日志索引；预留未来多人字段  
5) 日志层：运行级与步骤级日志目录，支持快速打开

> 对应文档：`工作流管理/02_架构与模块拆分.md`

## 7. “子工作流”能力：为什么要做、需要注意什么

### 7.1 为什么要做
当单个工作流越来越长时，把逻辑拆成多个可复用子工作流更可维护：
- 复用一段“公共步骤链”（例如：取数→清洗→落库）
- 让大流程可组合（主工作流 = 若干子工作流 + 少量特有步骤）

### 7.2 关键约束
- 必须做 **跨工作流循环依赖检测**：避免 A 引用 B、B 又引用 A 导致运行死循环。  
- 选择器要能 **搜索/过滤/最近使用**：否则工作流数量增多时不可用。

## 8. 典型使用场景（V1 目标形态）

### 场景 A：纯 Python 工作流
步骤 1~N 全部为 Python 脚本，按依赖/并行/前置编排执行。

### 场景 B：混合工作流（你提出的核心价值）
例如：
1) Python 清洗/计算  
2) Excel PowerQuery 刷新并保存产物  
3) Python 二次处理/出表  
4) Power BI Desktop 刷新 PBIX  

### 场景 C：复用子工作流
主工作流的某个步骤选择“子工作流”，直接复用另一条工作流作为一个步骤执行。

## 9. 质量与稳定性：我们在交流中明确的“底线”

### 9.1 错误处理策略（面向使用者）
- 能预判的错误尽量前置校验（路径不存在、参数 JSON 不合法、依赖缺失等）
- 错误提示必须“可操作”：告诉使用者下一步怎么修复
- 不允许“无反应”：即使被锁定也要给出提示（例如需要开启编辑）

### 9.2 验证策略（面向交付）
任何“改完了/已修复/可用”的结论都必须有验证证据（至少包含编译与冒烟启动）。  
典型验证：
- `python -m compileall 工作流管理/src`
- `python 工作流管理/src/main.py --smoke`（用于自动退出的冒烟启动）

## 11. 后续建议（V1.5/V2 方向）

当从个人走向内网小团队时，优先级建议：
1) 用户/权限/审计（最小可用：只读/可编辑两类角色）  
2) 任务队列与并发治理（避免多用户同时跑把机器跑满）  
3) 产物管理（归档、版本、清理策略）  
4) 远程运行与分布式（按需，成本最高）
