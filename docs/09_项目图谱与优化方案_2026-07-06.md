# 项目图谱与优化方案（待确认）

状态：方案已确认；当前进入 Slice 1（取消与终态一致性）和 Slice 4（测试环境与质量门）实施。

## 0. 优先级规则

本轮优化按以下顺序决策：

1. 正确性 / 稳定性
2. 速度 / 性能
3. 可维护性 / 精简
4. 新功能

原则：先让运行生命周期、取消、状态落库、外部进程清理可靠，再考虑性能和结构拆分；新功能只排在最后，不抢修复与稳定性的资源。

### 1.2 关键运行链路

#### GUI 手动运行

`btn_header_run` / `RunControlPanel` -> `ui.run_dispatch.on_run_requested` -> 后台线程 -> `ui.run_actions.run_engine_mode` -> `WorkflowEngine.run` -> `engine_core.run_orchestration.run_workflow` -> `execute_steps` -> `execute_single_step` / `execute_parallel_steps` -> `executors`.

#### 停止运行

UI 停止按钮 / Shift+F5 -> `run_dispatch.stop_workflow` -> `WorkflowEngine.cancel` -> `engine._cancelled=True` -> `step_execution` 中的 cancel watcher 映射到每个执行器的 `cancel_event` -> 执行器中断或返回取消 -> RunHistory 终态 `cancelled`。

本次已修复：并行批调度器在取消后仍继续补提交后续步骤的问题。现在取消后不再提交新的并行任务，并尝试取消尚未开始的 future。

#### 子工作流

父步骤 `sub_workflow_executor` -> 注入 `workflow_runner=engine.run_sub_workflow` -> 子工作流使用独立 `child_cancel_event` -> 父取消或超时时通知子工作流退出。

风险点：父子运行历史、活跃 run 栈、取消事件、后台线程宽限期必须保持一致，否则会出现父已取消但子仍后台运行。

#### 文件监听触发

`WatchManager` -> 文件变化稳定窗口 -> `trigger_cb` -> `engine.run_all(reason=watch)`；同时依赖 `watch_rules.py` 避免监听输出目录导致循环触发。

风险点：监听触发与手动运行竞争、运行期间文件变化吞并策略、watcher 生命周期清理。

## 2. 优化方案

### A. 正确性 / 稳定性

#### A1. 取消语义端到端收敛

目标：停止按钮点击后，系统进入明确的“正在停止”状态；不再提交新步骤；正在执行的步骤尽快收到取消事件；最终 RunHistory 和 StepLog 一致落到 `cancelled`。

建议：

- 将取消契约明确为三层：`run_cancelled`、`step_cancel_event`、`executor_result.cancelled`。
- 为 `scheduler -> step_execution -> executors -> run_history` 增加端到端测试，覆盖串行、并行、子工作流、Python 进程、Power BI、Excel。
- 对不支持立即中断的外部应用明确标记“已发出取消，等待外部进程退出”，避免 UI 显示“停止无效”。

优先级：最高。  
当前状态：调度器补提交问题已修复，仍需补齐端到端验证。

#### A2. 运行状态单一事实源

目标：减少 `engine._running`、`_stopping_in_progress`、`_running_workflow_id`、按钮状态、历史状态之间的漂移。

建议：

- 建立 `RunViewState` 或等价的 UI 状态投影，只从引擎信号和 RunHistory 更新。
- 将按钮状态、后台运行标签、面板锁定统一从 `ui.run_state` 推导。
- 对“停止中切换工作流”“停止并运行新的”“监听触发时已有运行”补 UI 状态测试。

优先级：高。  
原因：这类问题直接影响用户判断运行是否真的停止。

#### A3. RunHistory / StepLog 一致性

目标：任何终态下，运行历史和步骤日志不能出现“run=cancelled 但 step=running/pending”或“run=success 但步骤失败”的可见窗口。

建议：

- 将运行终态写入和 pending/running step 清理封装为一个数据层服务。
- 为取消、失败、异常收尾、DB 锁异常补一致性测试。
- 保留现有 `force_cancel_run_record`，但把“孤儿运行修复”与“正常取消收尾”边界写清。

优先级：高。

#### A4. 外部执行器清理策略

目标：Python 子进程、Excel COM、Power BI Desktop / REST 在取消、超时、异常时都有可审计的退出路径。

建议：

- 统一执行器取消返回：`exit_code=-1`, `error_message="用户取消"`，并在 `extra` 中标记 `background_risk` / `orphan_risk`。
- 对 Excel / Power BI 的“不可立即终止”场景做显式日志和测试。
- 继续使用 opt-in 本地集成测试验证真实 Excel 与钉钉，不放进默认 CI。

优先级：高。

#### A5. 导入导出 schema 与安全边界

目标：导入导出不破坏现有数据、不泄漏 Webhook、不吞掉 schema 错误。

建议：

- 为 `database_import_export.py` 拆出 schema validation / secret redaction / persistence 三段测试边界。
- 明确版本兼容策略：未知字段保留、拒绝、还是告警忽略。
- Webhook URL 继续走 `webhook_url_policy.py`，禁止绕过。

优先级：中高。

#### A6. 文件监听去抖与自触发防护

目标：监听目录变化不会重复触发、不被工作流输出反向触发、运行中变化策略可解释。

建议：

- 把“运行期间变化吞并策略”写成测试用例，而不是只写在 README。
- watcher 生命周期加入泄漏检查：启动失败、冲突拒绝、工作流删除、应用关闭。
- 日志里区分“变化被吞并”“变化触发新运行”“变化被冲突规则拒绝”。

优先级：中高。

#### A7. 测试环境可复现性

目标：开发环境中 `python -m pytest` 可收集运行，避免缺依赖时无法验证。

建议：

- 增加一个明确的本地测试准备命令，例如 `python -m pip install -r requirements-ci.txt` 或封装到 `tools/check_test_env.py` 输出修复建议。
- CI、README、guardrails 中统一推荐测试入口。
- 当前本机缺 `sqlalchemy`，这是验证链路的直接阻塞点。

优先级：中高。

### B. 速度 / 性能

#### B1. 并行批调度背压

目标：并行运行不超出工作流配置的 `max_workers`，取消后不继续消耗资源。

建议：

- 保持当前滑动窗口调度，不回退到一次性提交全部 future。
- 为取消、失败、超时补充“停止补提交”测试。
- 对批次执行增加轻量指标：提交数、完成数、取消数。

优先级：高于其他性能项，因为它同时服务稳定性。

#### B2. UI 高频刷新降噪

目标：日志、进度、步骤状态更新不会拖慢长工作流。

建议：

- 保留 `LogPanel` 的批量刷新策略。
- 检查 `workbench_board.py` / `step_table` 是否在每个 step signal 后全量重绘；若存在，改为局部更新。
- 长工作流下增加一次手工或脚本化性能 smoke。

优先级：中。

#### B3. 数据库读写分页与索引

目标：运行历史、步骤日志、工作流列表在数据量增长后仍可快速打开。

建议：

- 审查 `RunHistory`、`StepLog` 常用查询条件，补索引或分页。
- 历史列表只加载摘要，详情按需加载。
- 导出/备份避免一次性把大对象常驻内存。

优先级：中。

### C. 可维护性 / 精简

#### C1. 热点模块渐进拆分

目标：降低大文件修改风险，不做一次性大重构。

热点扫描显示：

- `src/ui/main_window.py`：1062 行
- `src/ui/workbench_board.py`：1034 行
- `src/ui/theme.py`：968 行
- `src/engine.py`：922 行
- `src/ui/step_editor.py`：917 行
- `src/database.py`：914 行
- `src/cli.py`：890 行

建议：

- 优先拆“稳定边界明确”的逻辑，不拆纯布局细节。
- `engine.py` 保持门面，但逐步把真实逻辑下沉到 `engine_core`。
- `database.py` 保持兼容入口，但新逻辑优先进入 `database_runs.py` / `database_workflows.py` 等子模块。
- UI 只在做相关功能时顺手提取控制器，避免为了行数而移动代码。

优先级：中。

#### C2. Trellis spec 补全

目标：把项目真实约定沉淀到 `.trellis/spec/`，后续优化不靠口头记忆。

建议：

- 先补 backend 的实际约定：运行状态、取消、数据库事务、外部执行器、日志。
- 不写理想化规范，只写当前项目真实模式和禁忌。
- 每次完成一个优化小任务后再更新 spec，避免一次性写空泛文档。

优先级：中。

#### C3. CLI / GUI 运行语义一致

目标：CLI 与 GUI 对运行模式、取消、通知、错误码的理解一致。

建议：

- `cli.py` 继续复用 `WorkflowEngine.run`，但把解析、展示、通知拆成小模块。
- 为 CLI 的取消信号、失败退出码、通知策略补契约测试。

优先级：中低。

### D. 新功能

新功能暂不进入第一批实施，除非它直接服务稳定性。

候选项：

- 运行详情页增加“停止请求已送达 / 等待外部进程退出 / 已取消”三段状态。
- 增加工作流运行诊断摘要：失败步骤、取消耗时、后台风险提示。
- 增强 dry-run：展示取消边界、并行批次、依赖关系风险。
- 增加可选的“从上次取消处继续”能力，但必须等 RunHistory / StepLog 一致性稳定后再做。

## 3. 整体审查后的调整

初始想法容易按单模块优化，例如只看 `scheduler` 或只看 UI 停止按钮。整体图谱审查后，方案做以下调整：

1. 取消不再作为单点 bug 处理，而是作为跨 UI、编排、执行器、数据层的系统不变量处理。
2. 性能优化中，只有“并行调度背压”提前，因为它同时影响稳定性；其他性能项排在状态一致性之后。
3. 热点拆分不作为第一优先级。大文件确实存在，但如果先拆结构再修状态，会放大回归风险。
4. 新功能全部后置。尤其“断点继续运行”依赖 StepLog 终态可信，不能在状态一致性前做。
5. 测试环境可复现性被提升为稳定性事项，因为无法运行测试会直接削弱后续每个优化的正确性证据。
