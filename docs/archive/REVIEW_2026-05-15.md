## 1. BUG / 错误专项

> 高置信度问题（≥70% 把握真实存在）。下方按严重度分级。

### 1.1 Critical（崩溃 / 数据丢失）

#### C1. `_run` finally 块同步复位 `_current_*`，与 Qt QueuedConnection UI 信号不同步
- 位置：`src/engine.py:728-735`
- 现象：顶层运行结束 finally 立即 `_current_run_history_id/_current_run_id/_current_trace_id = None`，但 `workflow_finished` 通过 QueuedConnection 异步派发到 UI；若期间 `start_watch` 触发新一轮 `run_all`，新运行立即占据 `_current_*` 并 emit `workflow_started`，UI 的 `set_running(False)` 与新一轮 `set_running(True)` 槽次序不确定 → 按钮"锁死 / 立即变停止"。
- 修复：finally 仅在 `prev_running == False`（即外层顶层）时清空 `_current_*`，或在 emit `workflow_finished` 后再加锁复位。

#### C2. WAL checkpoint 仅在 `create_run_history` 触发，写路径覆盖不全
- 位置：`src/database.py:807-822` vs `update_run_history` / `update_step_log` / `reorder_steps`
- 根因：SQLite WAL + `check_same_thread=False` 下，父 session commit 但 WAL 未合入主库时，子 session 跨线程读到旧状态。子工作流 `run_sub_workflow` 跨 session 读父 run 状态正是此场景。
- 修复：在 `update_run_history`（status running→success/failure）与 `update_step_log` 终态分支调 `PRAGMA wal_checkpoint(PASSIVE)`；或在 `init_db` 中将 `synchronous=NORMAL` 改 `FULL` 接受写惩罚。

#### C3. `scoped_session` 跨线程语义错误，session 持续累积
- 位置：`src/database.py:198-218`
- 根因：`with get_session() as session:` 退出只 rollback-on-exception，不调 `_scoped_session.remove()`。`_execute_parallel_steps` 借用 ThreadPoolExecutor worker 线程反复复用 session，并行步骤同一 session 中先后 commit 不同 step_log，任一回滚会拖走同 session 内未 commit 的写入。
- 修复：`get_session()` 退出统一 `_scoped_session.remove()`；database getter 返回 dict 或在 session 内 `expunge_all` + `make_transient`，避免 ORM 对象逸出。

### 1.2 High（功能失效 / 数据不一致）

#### H1. `force_stop_run` 不识别嵌套子工作流栈
- 位置：`src/engine.py:198-231`
- 根因：单变量 `_current_run_history_id` 在嵌套子工作流期间被覆盖；用户停的是父 run，命中的可能是子 run，于是父 run 被改 `status=cancelled` 但引擎仍跑子工作流。
- 修复：维护 `set[int] active_run_ids`，命中集合任一即 `self._cancelled = True`。

#### H2. `force_stop_run` 写库错过 WAL checkpoint，UI 看不到状态变更
- 位置：`src/engine.py:213-227` + `database.py:859`
- 修复：同 C2。

#### H3. `compute_batches` 把"已跑完阶段的步骤"当前置依赖来源
- 位置：`src/engine_core/batch.py:39-82` + `engine.py:947-948`
- 根因：`FROM_STEP` / `FROM_STAGE` / `RETRY_FAILED` 模式下 `steps` 是筛后子集；`compute_batches` 将"依赖必须来自子集"作为硬约束，对依赖于子集外步骤的节点抛 `DependencyError`，破坏 retry / from-step 可用性。HANDOVER 中"未充分测试的功能"很可能正是这类。
- 修复：进入分批前剔除子集外的依赖，或视为已完成。

#### H4. 文件监听 mtime 缓存导致漏触发
- 位置：`src/engine.py:441-488`
- 根因：`cache_key = int(time.monotonic() / 5)` 在同 5 秒窗口内 cache hit 直接返回上次结果，**不重新扫描**。cooldown < 5s 时连续两轮同窗 → mtime "永远不变"。
- 修复：缓存只缓存 stat 结果而非"是否扫描"；最简：直接删缓存层。

#### H5. 监听线程无 try/except 外壳，外部驱动器拔出即崩
- 位置：`src/engine.py:352, 401`
- 修复：`_watch_loop` 包裹 `while True: try: ... except: log; sleep(cooldown)`；`start_watch` 重入用 `is_alive()` 校验。

#### H6. `cancel()` 与 `wait_for_completion(10s)` 不闭合
- 位置：`src/engine.py:233-248`
- 根因：cancel 仅 set 标志，但 Excel `RefreshAll`、子工作流默认 1h timeout、重试 backoff sleep 60s 均不响应；10s 不够 → `shutdown(wait=False)` 强 kill 主进程，可能中段 sqlite commit。
- 修复：cancel 时 `shutdown(wait=True, cancel_futures=True)`；Excel 兜底 `taskkill /F /PID`。

#### H7. 钉钉通知同步阻塞主运行线程
- 位置：`src/engine.py:713-722` + `src/notifier.py:142-162`
- 根因：`_send_notification` 默认 timeout 10s，阻塞在 `_run.finally` → UI 显示 "running" 多 10 秒。
- 修复：`self._executor.submit(self._send_notification, ...)` 异步发，或独立 daemon thread。

#### H8. SubWorkflowExecutor 超时不能真正取消
- 位置：`src/executors/sub_workflow_executor.py:82-96`
- 根因：`future.result(timeout=...)` 抛 TimeoutError 后 `workflow_runner` 仍在跑，`with ThreadPoolExecutor` 退出会 `shutdown(wait=True)`，违背超时语义。
- 修复：超时分支 `executor.shutdown(wait=False, cancel_futures=True)` 后立即返回；把父 `_cancel_event` 传入子流。

#### H9. Excel 取消时 COM 时序问题导致 Excel 进程残留
- 位置：`src/executors/excel_executor.py:114-202`
- 根因：取消时 finally 调 `workbook.Close(SaveChanges=False)`，但 RefreshAll 仍在跑 → Excel 拒绝退出 → 异常被吞掉但 Excel.exe 持文件锁，下次 Open 报"被占用"。
- 修复：取消时记录 PID，finally 兜底 `taskkill /F /PID`。

#### H10. `Step.uid` 未加 `UniqueConstraint(workflow_id, uid)`
- 位置：`src/database.py:386-417` + `src/models.py`
- 根因：`import_from_json` 改动 uid 后 `ensure_single_script_step` 可能再插一条，产生重复 single_script。
- 修复：模型加 `UniqueConstraint('workflow_id', 'uid')`。

#### H11. CLI 信号 drain 使用 `processEvents(100 轮)` 时序不可靠
- 位置：`src/cli.py:338-343`
- 修复：`QEventLoop` + `QTimer.singleShot` 显式 drain，直到 `is_running=False` 且队列空。

#### H12. 嵌套子工作流 cancel 标志在出栈第一层即被清空
- 位置：`src/engine.py:592-733`
- 根因：finally 中以 `not self._running` 作为"是否复位 cancelled"条件，子工作流出栈时直接清零 → 父运行 cancel 失效继续跑剩余阶段。
- 修复：cancel 标志只在最外层（`prev_running == False`）出栈时复位。

## 2. 性能 / 架构专项

### 2.1 整体评估

- **架构成熟度**：5.5 / 10。功能稳定，重构在演进，但呈半吊子：模块拆出来但旧代码未瘦身，新模块接入面窄。
- **三大债务**：
  1. `engine.py` 仍 1469 行 God Object，43 个方法，`engine_core ↔ engine` 双向耦合。
  2. DB 层 N+1 与重复查询泛滥（CLI list、step_table.load_steps 等）。
  3. UI 直接 `with get_session()` + `from engine import WorkflowEngine`，分层被打穿。
- **建议节奏**：渐进改进（核心调度正确、测试可跑），优先做"无行为变化的提取"即可显著获益。

### 2.2 Critical（影响稳定性 / 性能基线）

#### CA1. UI 每次切换工作流触发 O(W×S) 查询（N+1）
- 位置：`src/ui/step_table/panel.py:410`、`src/cli.py` list 命令
- 现象：`load_steps()` 每次重载就调 `list_workflows()` 全表扫，仅为获取 `uid→name` 映射给 sub_workflow 步骤显示。100 工作流的库每次切换 / 拖拽 / 折叠都触发 100 行 SELECT。CLI list 100 工作流 → 101 次查询。
- 建议：`database.get_workflow_uid_name_map() -> dict`；CLI list 用 `selectinload(Workflow.steps)` 或聚合 `func.count`。切换延迟可降 5–20×。

#### CA2. `engine.py` God Object（43 个方法 / 1469 行）
- 现象：调度核心 + 文件监听 + 日志清理 + 阶段元信息 + 钉钉通知 + 子工作流嵌套 + cancel watchdog + 日志级别映射 + UI 信号策略全在一类。`compute_batches` 已抽离但 `engine.py:863` 反向 import 回去；`engine_core/__init__.py` 又从 engine 导入 WorkflowEngine → 双向耦合。
- 建议：按"五个边界"渐进拆分：
  - `engine_core/scheduler.py`：`_run / _execute_steps / _select_steps`
  - `engine_core/watcher.py`：`_watch_loop / _scan_*`
  - `engine_core/lifecycle.py`：`_cleanup_old_logs / log_dir 管理`
  - `engine_core/notification.py`：`_send_notification`
  - `engine_core/stage_meta.py`：`_build_stage_meta / _normalize_stage_uid`

  让 `WorkflowEngine` 退化为编排 + 信号层（< 300 行）。

#### CA3. UI 下钻 DB 与 engine，分层穿透
- 位置：`src/ui/step_table/panel.py:1098,1380,1435`、`src/ui/dag_view.py:260`、`src/ui/step_editor.py:542`
- 现象：UI 直接 `with get_session()` 跑 ORM 写入 + `compute_batches` 预校验；`step_table/panel.py` 共 59 个方法 / 1638 行混三层职责。
- 建议：抽 `src/services/step_service.py` 封装业务用例；`step_table/panel.py` 拆为 `panel.py`（容器，<400 行）+ `renderer.py` + `dnd.py`。

### 2.3 High

| # | 位置 | 问题 | 建议 |
|---|------|------|------|
| HA1 | `engine_core/batch.py:43-82` | `compute_batches` 退化至 O(n²)~O(n³)：每批 `min()` + 列表重建 + deps 线性检查 | 按 stage 预分桶 `defaultdict(list)`；pending 用 `set`；deps 转 `frozenset`；降到 O(n+edges) |

### 2.4 Medium

- **MA1** 四个 executor 接口非对称：取消轮询样板被复制三遍，子流又用 `concurrent.futures` 完全不同范式。基类提供 `_run_with_cancel(target_callable)` 模板方法。
- **MA2** `Workflow.max_workers` 字段是死字段，未被使用；engine `max_workers = min(32, cpu+4)` 写死。按 batch 创建临时 ThreadPoolExecutor 或维护 per-workflow 池。
- **MA3** `constants.py` 接入面窄：20 个常量只有 `MAX_LOG_LINES` 在用；Excel/PowerBI/SubWorkflow 超时仍硬编码在 executor。一次性 PR 替换。
- **MA4** `cli.py` 调 `engine._run` 私有方法 + `processEvents` 轮询；CLI/GUI 未真正共享执行入口。把 `_run` 升级为公开 `run(...)`；CLI 用 `QEventLoop` 阻塞等信号。
- **MA5** Schema 索引：缺 `(workflow_id, stage_uid, order)` 与 `(step_id, status)`；1 万行 StepLog 时 skip_on_success 检查 ~50ms。
- **MA6** `main.py` import 阶段就拉起整个 UI 子树（13 组件）+ engine + database，冷启动 ~600–900ms；CLI 因 `WorkflowEngine` 继承 QObject 必须 `QApplication([])`，无法 headless。建议 engine_core 用 callback / blinker，GUI 层包 QObject 适配。

### 2.5 Low

- **LA1** `build.spec`：`hiddenimports` 未列 `pywinauto / networkx / requests / engine_core.batch / executors.*`；建议 `--collect-submodules executors --collect-submodules engine_core`。
- **LA2** `APP_DATA_DIR/工作流管理` 含中文，Win 短路径解析偶发异常；建议 ASCII 路径（`LOCALAPPDATA\WorkflowManager\v3`）。
- **LA3** `ErrorDiagnostician` 硬编码 `if keyword in message` 顺序匹配 → `(regex, type, fix)` 三元组 + 注册函数。
- **LA4** `SubWorkflowExecutor` 每次新建 `ThreadPoolExecutor(max_workers=1)` 仅为 timeout → 改用 `_cancel_event` 即可省一线程。
- **LA5** `dag_view.update_dag` 切换工作流彻底 `deleteLater()` 重建（i5 笔记本 ~150ms / 50 节点）→ 增量 diff。
- **LA6** `_cleanup_old_logs_async` 每次 `run_all` 起线程 → 改 QTimer.singleShot 60min。

## 3. UI / UX 专项

### 3.1 整体评估

- **UX 成熟度**：6.5 / 10。iOS Minimal 取向，对财务 / 数据分析师群体审美匹配尚可。
- **目标用户画像**：把多个 Python / Excel / Power BI 任务串成自动化流水的数据 / 财务岗。
- **三大痛点**：
  1. "编辑模式"全局开关错误地承担"防误操作"职责 → 几乎所有写操作都被门禁卡住，新手所有按钮置灰。
  2. **崩溃级 Bug `self._dark` 错拼**（同 BUG-C1，但在 UI 维度严重度 P0）。
  3. **首次使用空白**：无 onboarding、无示例工作流、空状态文案仅"请选择一个工作流"。

### 3.2 P0（崩溃 / 阻断）

#### U-P0-1 `self._dark` 错拼导致对话框崩溃
- 位置：`src/ui/main_window.py:362,526,666,674,679,704,728,733,751,755,808`
- 现象：`__init__` 定义 `self._dark_mode`，但下游 `msg_*` 调用传 `self._dark`，命中即 AttributeError，覆盖"未选工作流警告 / 导入导出 / 强制停止 / 关闭确认"等高频路径。
- 修复：统一 `self._dark_mode`，或加 `self._dark = self._dark_mode` 别名并同步 dark 切换。

#### U-P0-2 `LogPanel.open_step_log` 方法缺失
- 位置：`src/ui/main_window.py:641` 调用，`src/ui/log_panel.py` 无定义
- 修复：在 LogPanel 实现 `open_step_log(workflow_id, step_id)` 打开 stdout/stderr，或让 ErrorSummaryDialog 走兜底分支。

#### U-P0-3 `reply == 16384` 魔法数字遍布多处
- 位置：`main_window.py:707`、`workflow_list.py:284`、`step_table/panel.py:1036`、`run_history.py:374`、`workflow_config.py` 等
- 风险：Qt 升级 / 绑定差异即静默失效，"是"被当"否"，破坏性操作可能被错误执行 / 取消。
- 修复：直接比较 `QMessageBox.Yes`，并让 `msg_question` 返回 `StandardButton`。

### 3.3 P1（严重影响日常）

#### U-P1-1 "编辑模式"心智模型不清且过度门禁
- 一个全局开关同时管"新建 / 克隆 / 删除 / 拖拽 / 编辑字段 / 保存配置"；IosSwitch 43×24px 在左上角，违反 Fitts。
- 建议：(a) 默认开启，仅"删除工作流 / 清空历史 / 强制停止"独立二次确认；(b) 若保留则放工具栏右上，加 Ctrl+E 快捷键 + 首次发现气泡。

#### U-P1-2 左侧 Run 控制按钮 30px 过低，主次按钮无区分
