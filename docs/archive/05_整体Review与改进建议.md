# 工作流管理应用：整体 Review 与改进建议（BMAD + Brainstorming）

> 本文档用于：在“用途阶段（手动）+ 执行批次（自动）”双层模型落地后，对现有应用的**功能性、逻辑闭环、可用性与可扩展性**做一次结构化评估，并给出可执行的改进路线图。
>
> 说明：本文会刻意把“用途阶段”与“执行批次”分开描述，避免概念混淆。

---

## 0. TL;DR（你关心的结论）

- 目前已具备：**用途阶段分组框住展示、拖拽改归类+顺序、严格禁止依赖未来阶段、启用并行即可同依赖层自动并行、JSON 可携带阶段信息**，并且有基础单测保障。
- 当前最需要补的闭环：**阶段管理的“顺序调整/删除迁移”**、**依赖配置的可理解性（可视化/引导/修复路径）**、**运行失败后的可恢复操作（重试策略与失败定位）**。
- 建议路线：先把“日常编排闭环”做扎实（P0），再做“多人/内网”前置能力（P1），最后才做“高级可视化与产物管理”（P2）。

### 已按优先级推进（本轮）
- ✅ 依赖摘要 + 双击定位（步骤编辑器）
- ✅ 失败闭环：失败汇总弹窗支持定位/打开步骤日志/一键重试；运行历史支持“查看失败步骤”
- ✅ 删除阶段迁移向导：删除非空阶段时可选择迁移目标阶段后删除

## 1. 现状盘点（Current State）

### 1.1 领域模型（已确认）

**A. 用途阶段（Stage by Purpose）**
- 人为定义：用于归类（采集/清洗/建模/发布……）
- 有顺序：Stage 1 → 2 → 3…
- 影响执行：**后一用途阶段默认等待前一用途阶段全部完成**

**B. 执行批次（Batch by Dependency）**
- 由 `compute_batches()` 根据依赖 + Gate + 并行开关自动计算
- 表格与 DAG 中显示为 `B#`，用于解释“同批并行/串行/Gate”

### 1.2 当前能力清单（已落地）

- 用途阶段：
  - 默认阶段自动补齐；老数据不破坏旧行为（单阶段等价于原来）
  - 步骤列表按用途阶段“卡片框住”分组展示，拖拽时高亮目标阶段
  - 阶段操作：重命名、插入前/后、删除（仅空阶段；默认阶段不可删）
- 拖拽编排：
  - 拖拽默认只改“用途阶段归类+顺序”
  - 写库前在事务中做 `compute_batches()` 预校验；失败回滚并弹窗说明
- 引擎执行：
  - `parallel_enabled=True` 时：同依赖层自动并行（无需步骤级并行开关）
  - Gate 优先且单独执行
  - 严格规则：禁止依赖未来用途阶段
- 可解释性：
  - 步骤列表：`Sx-y`（用途阶段+阶段内顺序）+ `B#`（执行批次）
  - DAG：按批次泳道展示，并在节点下方标注所属用途阶段（S# 名称）
- 质量保障：
  - 单测覆盖：用途阶段门槛、同阶段自动并行、未来阶段依赖报错

## 2. “逻辑与操作闭环”检查（闭环=用户不会卡住）

> 下面是按真实使用路径梳理“用户能不能完成任务、遇到错能不能自救”的检查框架。

### 2.1 防误操作闭环：编辑模式（OK）
- 编辑模式关闭：禁止所有写操作，并有明确提示
- 建议增强：把“为什么禁用”统一成同一种提示组件（状态栏 + 一次性弹窗）

### 2.2 编排闭环：用途阶段 + 顺序（基本 OK，但还缺关键能力）
- 已有：拖拽跨阶段改归类、插入阶段、阶段重命名、空阶段删除
- 缺口（高频）：
  1) **调整用途阶段顺序**（拖拽阶段/上移下移）
  2) **删除非空阶段**（提供“把步骤迁移到…”后再删除）
  3) **阶段内/跨阶段批量移动**（一次拖多行或“移动整个阶段的步骤”）

### 2.3 依赖闭环：配置 → 理解 → 修复（部分缺失）
- 目前 UI 只提供“依赖上一步（上一）”快捷，对新手友好
- 风险：一旦出现复杂依赖或跨阶段依赖报错，用户不知道“怎么修”
- 建议补齐：
  - 在步骤编辑器提供“依赖可视化摘要”（我依赖谁 / 谁依赖我）
  - 报错弹窗给出“可点击的修复动作”（定位到步骤、自动移动到合规阶段、或一键清理非法依赖）

### 2.4 运行闭环：启动 → 失败定位 → 重试恢复（需要增强）
- 已有：运行模式（全流程/从步骤开始/只跑步骤/重试失败）
- 缺口（关键）：
  - 失败时“下一步怎么做”不够明确：需要把失败步骤、日志目录、重试入口串起来（减少用户来回找）
  - 对“用途阶段门槛导致的等待”缺解释（用户会误以为卡住）

## 3. 主要问题与风险（Risks）

### P0 风险（会影响日常可用）
1) 用途阶段顺序不可调整 → 很难长期维护流程演进
2) 复杂依赖缺少引导与修复路径 → 用户一旦配错就“只能靠试”
3) 运行失败后的恢复路径分散（日志/失败步骤/重试）→ 操作成本高

### P1 风险（影响扩展到内网小团队）
1) 并发编辑冲突：SQLite 本地单机无冲突策略（后续要加锁或升级 DB）
2) 权限与审计缺失：多人场景需要操作记录（谁改了什么）

### P2 风险（高级功能）
1) DAG 复杂度上升后可读性下降：需要过滤/折叠/聚合
2) 产物管理/资源管理一旦做不好会变成“另一个文件管理器”

## 4. 改进路线图（BMAD 风格：Epics → Stories）

> 目标：功能做加法，但操作和界面做减法。优先提升“可维护、可解释、可恢复”。

### Epic 1（P0）：用途阶段编排闭环

**Story 1.1：用途阶段顺序可调整**
- 需求：阶段标题条支持“上移/下移”或拖拽排序
- AC：
  - Given 有多个阶段，When 调整阶段顺序，Then 运行顺序随之变化（stage barrier 生效）
  - Then 现有步骤归类不变（只变阶段 order）
  - Then 若导致“依赖未来阶段”，给出阻止/回滚提示

**Story 1.2：删除阶段时的迁移向导**
- 需求：删除非空阶段时，弹出“把该阶段所有步骤移动到…（目标阶段）”后再删除
- AC：
  - Then 迁移在事务中完成并做 `compute_batches()` 预校验
  - ✅ 已实现

### Epic 2（P0）：依赖配置的可理解性与修复

**Story 2.1：步骤依赖摘要（我依赖谁 / 谁依赖我）**
- 位置：步骤编辑器
- AC：
  - Then 点击某依赖可定位到对应步骤（列表选中 + DAG 高亮）
  - ✅ 已实现（双击条目定位到步骤）

**Story 2.2：错误弹窗“可操作修复”**
- 场景：跨阶段依赖、循环依赖、依赖缺失
- AC：
  - Then 弹窗提供至少 1 个安全修复动作（例如“移动步骤到同/前一阶段”或“清除非法依赖”）

### Epic 3（P1）：运行恢复闭环

**Story 3.1：失败步骤聚合与一键重试**
- 位置：右侧日志/运行历史
- AC：
  - Then 失败后可一键跳转到失败步骤日志 + 一键重试失败步骤
  - ✅ 已实现（失败汇总弹窗 + 运行历史右键）

**Story 3.2：用途阶段等待解释**
- AC：
  - Then 运行中若进入“下一用途阶段门槛等待”，日志/状态栏明确提示“正在等待上一用途阶段完成”

### Epic 4（P1）：团队化预留（不做重功能，做“能升级”）

- 变更审计：记录 workflow/step/stage 的变更日志（时间、操作者、字段差异）
- 冲突策略：至少做到“提示冲突+最后写入者提示”，后续可升级到服务端

### Epic 5（P2）：DAG 可用性提升（可选）

- 节点过滤：按用途阶段/类型/关键字过滤
- 视图折叠：按用途阶段折叠为一个大节点（点开再展开）

## 5. Decision Log（关键决策记录）

1) 阶段含义：采用“用途阶段（手动）”而非“依赖层自动阶段”
2) 执行语义：用途阶段顺序影响执行（stage barrier）
3) 并行语义：开启并行即“同依赖层自动并行”，无需步骤级并行 UI
4) 依赖规则：严格禁止依赖未来用途阶段（避免语义混乱与不可预测调度）
