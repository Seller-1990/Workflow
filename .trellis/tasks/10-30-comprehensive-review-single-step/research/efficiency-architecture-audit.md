# UI 性能与架构审查（efficiency-auditor）

日期：2026-10-30
范围：当前工作树的 UI、动画与区间运行改动、启动/高频刷新、相关跨层契约。只读审查；未修改源码、测试或 Git。`run_dispatch.py`、`step_editor*.py`、`risk_path_review.py` 仅读取以核对边界，未修改。

## 审查依据

- 任务契约：`prd.md` 第 6–14、17–22 行；`research/recovery-and-single-step-summary.md` 第 16–31 行。
- 规格：`.trellis/spec/backend/quality-guidelines.md`（运行状态投影、终态解锁、取消契约）；`guides/code-reuse-thinking-guide.md`；`guides/cross-layer-thinking-guide.md`。
- 阅读了当前 `src/main.py`、相关 `src/ui/*.py`、步骤筛选/执行信号顺序，以及所有变更 UI 文件的 `git diff`。
- 性能数据区分「调用计数/复杂度实测」与「墙钟时间」；离屏合成数据不外推为真实用户设备卡顿时间。

## 结论摘要

确认 6 项值得处理的问题：

1. **高：看板加载与状态刷新均为 O(n²)，实测调用次数随步骤数二次放大。**
2. **中：每次运行的全局进度初始总数缺失，实际选步总数已经存在但没有传给 UI。**
3. **中：日志定时/阈值“批量”最终仍逐行 `QTextEdit.append`，批量边界失效。**
4. **中低：新增颜色动效逐帧重写 QSS，触发固定次数的样式解析/重级联。**
5. **中低：看板吞掉批次计算异常后展示看似合法的顺序批次号，与步骤表的错误呈现不一致。**
6. **低：工作流切换共享了 ORM 数据，但仍重复计算阶段映射与批次；应复用纯计算结果，而非再引入缓存层。**

不建议回退动画不可见降级、运行锁/状态投影、历史异步加载、步骤表行索引或防御性生命周期处理；它们承载真实行为契约。启动路径未发现由本次 `QFont` 同源改动引起的高置信回归，但当前首次选中工作流会同步构建步骤表与看板，先修第 1/6 项比引入新的懒加载框架更有证据。

## 1. 高：看板增量构建和单步状态更新反复重扫全部卡片

**状态：confirmed（复杂度 + 调用计数实测）**

### 证据与机制

- `src/ui/workbench_board.py:361-366`：每 `add_card()` 都调用一次 `refresh_minimum_height()`。
- `src/ui/workbench_board.py:368-379`：该刷新遍历当前泳道的**全部已有卡片**并逐张重算，再刷新整个泳道。
- `src/ui/workbench_board.py:614-633`：逐卡增量构建；同阶段第 k 张卡会重扫前 k 张，因此仅单阶段加载就是 `1 + ... + n = O(n²)`。
- `src/ui/workbench_board.py:621-623`：每个阶段再次线性过滤 `ordered_steps`，多阶段时额外为 O(阶段数 × 步骤数)。
- `src/ui/workbench_board.py:166-184,714-725`：单卡状态/耗时变化后，除了该卡自身，还调用整泳道 `refresh_minimum_height()` 和全板 `_sync_board_minimum_size()`。
- `src/ui/workbench_board.py:781-807`：全板同步再次遍历所有泳道，并由泳道刷新重扫全部卡片。因此 n 个步骤各完成一次，更新路径也是 O(n²)。

### 频次与成本

- 工作流切换/启动首次选择、步骤保存、增删/排序、主题相关重载，以及运行开始重置和每个步骤开始/结束。
- 离屏合成 1 阶段 40 步、禁用数据库差异的探针结果：
  - `load_workflow()`：**900 次** `StepCard.refresh_minimum_height()`、41 次泳道刷新；本机该次加载 145.9 ms（仅该环境的参考值，不作为普遍延迟承诺）。
  - 再对 40 步各发一次 success：**3,280 次**卡片高度刷新、80 次泳道刷新、40 次全板尺寸同步。
- 计数已从当前代码直接测得，不是由注释推测。

### 最小修复

1. 构建阶段先按 `stage_uid` 一次分桶；逐卡只做 `addWidget/append`，每张卡初始高度最多计算一次。
2. 一个泳道完成加卡后统一更新一次计数、进度和高度，全部泳道结束后统一 `_sync_board_minimum_size()` 一次。
3. 运行态只重算发生变化的卡及其所属泳道；若该步没有引起尺寸变化，不做全板同步。可保留一个合并到下一轮事件循环的尺寸同步，而不是每步同步执行。
4. 添加调用计数回归：同阶段 n 卡加载的卡高度刷新应为 O(n)，非全尺寸变化的状态更新不得触碰无关泳道。

### 对抗性反例与边界

不能把所有高度刷新都删掉：状态徽章和耗时徽章的显隐可能改变卡高（`166-184,230-239`），而全板最小高度又决定滚动区域。正确优化是**只在尺寸可能变化时重算受影响泳道，并保留最终全板同步**，不是把 `_sync_board_minimum_size()` 当冗余删除。现有 `tests/test_workbench_board.py:160-189` 只验证重复同值更新会短路，无法发现上述跨卡放大。

## 2. 中：运行开始信号没有实际选步总数，全局进度先错误地变成 0/1

**状态：confirmed（信号顺序 + 直接生命周期探针）**

### 证据与机制

- 执行层在发开始信号之前已经完成选步：`src/engine_core/run_orchestration.py:291-318`；实际 `len(steps)` 已知。
- `workflow_started` 仍只发 `(workflow_id, run_id)`：`src/engine.py:166-172`、`src/engine_core/run_orchestration.py:355-357`。
- UI 读取从未在代码库中赋值的 `_running_step_total`，回退为 0，再强制传 1：`src/ui/run_lifecycle_controller.py:167-170`。
- 进度信号只在步骤/并行批次完成后发出：`src/engine_core/run_orchestration.py:593-594,611-612`。因此首个步骤执行期间没有真实总数。

直接调用 `on_workflow_started()` 的探针结果：

```text
{'run_workflow_id': 1,
 'logical_max_after_start_without_total': 1,
 'logical_value': 0,
 'progress_text': '0%'}
```

### 频次与影响

- **每次 UI 运行**都会发生，区间运行尤其明显：UI 已经选定范围，却仍显示 0/1。
- 首个步骤较慢时，整个首步期间都显示错误的总量/百分比。
- 若第一步在产生 `progress_updated` 前异常并提前终止，错误初值可一直保持到结束态覆盖。

### 最小修复

从执行层已经选定的 `steps` 传递实际总数给运行开始元数据（扩展开始信号或引入等价、明确的运行上下文通知），再由 `show_running(total)` 消费；不要用 UI 的全工作流步骤数替代，否则区间/单步/重试仍错误。保持子工作流 `RunSignalPolicy` 语义不变，并覆盖 full、range、only_step、retry 的总数测试。

### 对抗性反例与边界

若第一步立即完成，错误初值只是一瞬间，这不构成“没问题”：慢首步与首步早退均是现有合法路径。也无需为了传总数而复制一套 UI 选步逻辑；执行层已经拥有权威结果，复用该事实可避免跨层规则漂移。

## 3. 中：日志批量刷新仍逐行操作 QTextDocument

**状态：confirmed（调用计数实测）**

### 证据与机制

- 定时器/32 条阈值只减少 `_flush_pending()` 调用：`src/ui/log_panel.py:32-37,163-179`。
- 真正的 flush 在 `src/ui/log_panel.py:181-188` 对每条 HTML 分别调用 `self.log_text.append(html)`；过滤/搜索重渲在 `287-295` 同样逐条 append。
- `QTextEdit.append()` 每次都会向文档追加块并触发相应文档/布局工作，所以当前实现没有兑现第 32 行“批量刷新避免逐行 append 布局风暴”的设计目的。

探针结果：

```text
两条稀疏日志：定时 flush 前 append=0；flush 后 append=2
100 条日志：append=100（而不是一次批量文档写入）
```

### 频次与成本

- 高频日志每 32 条或每 50 ms 触发；脚本输出越密集越明显。
- 搜索/级别过滤会对最多 2,000 条缓存逐条重插。
- 本次确认的是**操作放大**，未把它包装成已测得的毫秒卡顿。

### 最小修复

在 flush 内用末尾 `QTextCursor` 一次性插入已转义文本/HTML 块，或用经验证等价的一次文档插入 API；保留 50 ms/32 条入口节流、级别颜色、文本转义、2,000 块裁剪和滚到底部。重渲复用同一批量渲染辅助函数。增加“两条待写日志只发生一次文档插入”的测试，而不只测最终文本。

### 对抗性反例与边界

定时器确实降低了刷新频率，因此不能称它“完全无用”；问题在批量边界被最后的循环破坏。若简单用 `"<br>".join(...)` 替换，可能改变 QTextEdit 的段落/空行与裁剪语义，修复后需比较 `toPlainText()`、颜色与块数，不能只追求调用次数为 1。

## 4. 中低：颜色动画以逐帧 QSS 重解析实现，成本与设计目标相反

**状态：confirmed（逐帧写入与次数实测；未宣称用户可见卡顿）**

### 证据与机制

- 通用悬停：`src/ui/motion.py:166-182`，每个插值都 `setStyleSheet()`，结束再清空一次。
- 卡片左条：`src/ui/workbench_board.py:199-224`，每个状态颜色插值都重写自身 QSS。
- 全局进度颜色：`src/ui/global_progress.py:94-120`，每个插值重新设置 `QProgressBar::chunk` 样式。
- 离屏完整动画探针：150 ms 悬停共 **11 次** QSS 写入（含清理），200 ms 全局进度颜色切换共 **13 次**。次数随帧调度可变化，但每次值变化都进入 QSS 路径是确定事实。

### 频次与成本

- 每次指针 enter/leave、每个卡片运行状态变化、每次运行开始/结束颜色变化。
- 并行步骤最多可让多张卡同时进入此路径；QSS 重写不仅是绘图，还涉及样式解析与重新级联。

### 最小修复

优先把需要动画的窄条/背景变成轻量自绘属性并只 `update()`，或使用已有的 Qt 图形效果而不反复解析 QSS；保留结束交还主题 token 的行为。先优化卡片左条和全局进度这种高频/小面积绘制，不必抽象一个全应用动画框架。补充终态颜色与主题切换测试，防止视觉优化变成颜色回归。

### 对抗性反例与边界

控件很小、并发卡片不多时，这未必成为最大瓶颈；优先级低于第 1–3 项。也不应删除 `can_animate()` 或结束后清内联样式：前者避免构建/恢复时无意义动画，后者保证主题/选择状态重新由 QSS 接管。要删的是**逐帧样式重编译**，不是动画生命周期防线。

## 5. 中低：看板批次计算失败被静默转换成看似有效的顺序批次号

**状态：confirmed（控制流与跨组件契约对照）**

### 证据与机制

- `src/ui/workbench_board.py:896-902` 对 `compute_batches()` 的所有异常一律返回空映射。
- 调用处在 `src/ui/workbench_board.py:624-627` 用 `within_idx` 补上 `B1/B2/...`，用户无法区分这是实际执行批次还是异常后的序号。
- 同一份数据在步骤表中的行为不同：`src/ui/step_table/panel.py:200-224` 会明确显示“批次计算失败/异常”及诊断信息。

### 频次与影响

- 依赖环、无效依赖或其他批次计算异常时触发；不是正常每次刷新。
- 看板继续可操作是合理的，但伪造合理 B 编号会误导用户对执行并行/屏障的判断，也掩盖配置错误。

### 最小修复

保留“异常时仍可浏览卡片”的降级，但让结果显式携带失败状态：显示与步骤表一致的非阻塞警告，批次标签改为未知/不可用而非顺序 B 号；记录可诊断异常。只捕获预期配置/依赖异常，编程错误至少记录，不宜无日志吞掉。

### 对抗性反例与边界

不能因“fallback 会掩盖错误”就直接抛出并让看板空白；导航/编辑仍应有降级 UI。这里要修的是**静默且语义失真的 fallback**，不是删除所有容错。

## 6. 低：同一次工作流加载共享 ORM 查询，却重复做相同纯计算

**状态：confirmed（静态调用链；未单独测量批次算法耗时）**

### 证据与机制

- 主窗口已一次加载并共享 workflow/steps/stages：`src/ui/main_window.py:228-240`，这是正确边界。
- 步骤表仍自行获取阶段映射并计算完整 batches：`src/ui/step_table/panel.py:200-216`。
- 看板随后再次 `get_stage_order_map()`、`compute_batches()`：`src/ui/workbench_board.py:596-607`。
- 两边从同一份步骤生成同类 `step_id -> batch_index`，属于可复用纯计算，不是必要的数据库/视图隔离。

### 频次与成本

首次选择/切换工作流及多种重载路径发生；成本随步骤和依赖图规模增长，并包含一次可避免的重复查询。当前没有证据把它列为比第 1 项更大的启动瓶颈。

### 最小修复

让现有主窗口预加载流程同时计算一次 `stage_map` 和批次映射，作为不可变展示元数据传给步骤表/看板；保留各面板独立使用时的现成回退路径。先抽展示用纯辅助函数，不引入另一套持久缓存或新服务层。

### 对抗性反例与边界

步骤表需要从批次提取依赖提示，看板只需要编号，视图模型并非完全相同；应共享**共同的批次结果**，而不是强行合并两种渲染逻辑。直接删除面板回退查询会破坏现有测试和独立使用入口，不建议。

## 明确驳回的“冗余/问题”猜测

1. **不删 `can_animate()` 与不可见直接终态。** 它不是无意义防御；构建、状态恢复和隐藏标签页都会经过，能避免无消费者动画及测试不稳定。折叠动画实测可到达 height=44、body 隐藏的正确终态。
2. **不删运行状态投影/重复 setText。** `set_header_run_button_state()` 统一 idle/running/stopping 是质量规格明确要求；`BreathingChip.setText()` 对相同文本已短路。幂等刷新保证 started/finished、主题恢复和停止链一致，不等同无效重复。
3. **不删步骤表 `_row_by_step_id`。** `src/ui/step_table/panel.py:469-487` 已是 O(1) 定位；看板的全局扫描问题不能类推到这张表。
4. **不把日志 `deque(maxlen)` 当冗余。** 它服务过滤/搜索/导出和有界内存；应修文档批量插入，不是回到只保留 QTextEdit 内容。
5. **不要求看板主题刷新也回放所有运行状态。** 看板卡片自己保留 `_status`、徽章、进度，主题切换只换颜色/图标；步骤表因行重建才需要 `main_window_setup.py:701-723` 的回放。把两边都回放反而可能引入无意义状态写入。
6. **不删区间运行的跨层转发或“非区间保持旧调用形态”。** `engine_core/run_orchestration.py:291-298` 保留旧调用形态能兼容实例级测试替身；这是有消费者的接缝。真正需要改的是权威选步结果尚未传给进度 UI。
7. **不建议合并 RunWorker 与 run_actions 或恢复更大的 MainWindow。** 当前后台线程边界与引擎模式分发很小且可测；抽象数量不是独立问题。重复纯计算和隐式总数才造成实际维护成本。
8. **未把 `QTimer.singleShot(0)` 一律视为浪费。** 历史加载和延迟尺寸同步用于避免信号到达时重入；问题在无合并的全量重复工作，而非异步机制本身。

### 只读探针

## 建议处理顺序

1. 看板构建/状态更新的 O(n²)（最大确定收益）。
2. 实际选步总数的跨层传递（正确性，且区间运行直接相关）。
3. 日志真正批量文档插入（高频路径）。
4. 看板失败批次的真实呈现、逐帧 QSS 替换。
5. 共享批次计算结果；不开展无证据的大规模 UI 重写。
